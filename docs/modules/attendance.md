# Employee attendance

Attendance is independent of salary, bonuses, penalties and wallet accounting. Employee directory cards show Clocked in / Clocked out with the corresponding AM/PM time, or Not clocked in when no arrival is recorded; clocked-out cards retain the arrival time underneath. Loading and unavailable states remain explicit. Employee profiles show today's estimated attendance and a dedicated Attendance history dialog. Add employee and Edit employee contain device linking beside salary/status fields. Settings → Business profile contains attendance rules and device management.

## Workdays and summaries

Two independent business times define attendance in the business IANA timezone:

- **End of attendance day** is the boundary between one attendance date and the next. Midnight gives calendar days; 04:00 keeps overnight punches through 03:59 with the preceding date.
- **Clock-out cutoff** divides that attendance day into arrival and departure periods. Strictly before it, retain the earliest punch as clock-in. At or after it, retain the latest punch as clock-out. A threshold earlier than the day boundary falls on the following calendar date. The two times must differ.

New linked uploads reduce directly into the single `(tenant, employee, work_date)` row: intermediate/repeated punches create no event rows and do not change its revision. Out-of-order uploads can move arrival earlier or departure later. Locks serialize reductions across machines; device stamps advance only after the packet commits. Unlinked device User IDs remain discoverable, but their punches are not saved or adopted later. Raw pre-rework evidence remains immutable for audit; the migration reclassifies its derived daily endpoints using the two periods without rewriting source events or manual adjustments. `scan_count` now counts the retained endpoints (0–2), not physical scans.

A missing clock-in or clock-out stays missing. No estimated clock-out is invented at the boundary. Worked time is zero unless both endpoints exist. A departure-only row can later gain a delayed valid arrival. Future punches more than ten minutes ahead are skipped from attendance; their retries do not become saved evidence. Terminal dates must be 2000–2100. Missing punches alone do not establish absence. Machine time and timezone must be correct.

Rule changes start with the next attendance day and keep dated rules for delayed uploads. A boundary transition also updates the open preceding day's ending boundary to keep adjacent days contiguous; its arrival/departure threshold remains unchanged. Timezone changes are rejected after attendance exists. Workdays use actual instants across DST. Manual corrections remain explicit audited overrides and take priority over later device reductions; weekly/monthly histories and activity read the same daily projection. No salary, stock, wallet or journal recognition is changed by attendance.

## Effective linking and corrections

`attendance_links` stores immutable starts and one-way ends for each device/User ID/employee association. New links start at database server time; prior punches remain unassigned. A punch belongs to a link only within `[linked_at, unlinked_at)`, regardless of arrival time. Unlinking preserves old attendance and previous associations. Reusing a machine User ID starts another period and cannot transfer earlier evidence. Current links are unique by device/User ID and device/employee. Device locks serialize registration, removal, linking and ingestion. Employee creation and initial linking share the existing idempotent `save_employee` transaction; a failed link rolls back the employee too.

The one-time migration preserves previously adopted historical associations, which had no recorded effective start, with an explicit unbounded start. It does not backdate new links. The old departure-threshold configuration is retained in configuration audit before normalization to midnight. Raw machine events, stock and financial evidence are fingerprint-checked for preservation.

Users with the trusted `attendance:manage` capability can use Attendance history → Edit history. The date editor loads current times, a revision and the server-calculated workday window even for an empty day. Separate calendar-day/hour/minute controls offer only choices in that window and no future times; arrival choices precede a selected departure and departure choices follow a selected arrival. Existing endpoint seconds are preserved until edited. Clock-in must precede clock-out; departure may equal the day end. The editor shows consistent dated 12-hour times and the complete allowed window, then the standard confirmation dialog shows before/after values and the reason. SQL independently verifies trusted RBAC membership, tenant, date, ordered times within the saved day, future-time restrictions and revision. Empty clock-in/out marks a day as not attended. Append-only `attendance_adjustments` retain actor, reason, before values, final values and idempotency request ID; original events are never rewritten. Recent corrections are visible in the editor. A retry uses the original request ID. Concurrent or delayed device changes reject stale edits.

Activity contains stable `employee:date:in/out` identities, rather than every raw punch. A later clock-out updates that day's existing item. Capability gates keep payroll-only readers out of attendance and employee-only readers out of financial evidence. Histories filter and paginate on the server: attendance 12 periods/page, activity 12 items/page, raw-event audits and unlinked device users 25/page. Indexes cover tenant/employee/date, effective links, raw enrollment/date ranges, revisions and audit lookups.

## Direct ADMS and security limitation

The canonical `attendance-receiver/server.mjs` remains a machine-initiated ADMS PUSH service behind the existing Caddy HTTPS host on port 443. The connected MB20-VL's existing server address stays `api.lpg.144.79.249.4.sslip.io:443`; standalone port 4370 is unrelated and must not be publicly forwarded. No local relay, shop public IP, authentication key, firmware change or new infrastructure is required.

A Settings manager registers an exact serial into their trusted business, then explicitly approves it. Existing authorized machines remain approved during migration. Unregistered, unapproved, disabled and removed registrations are rejected before upload parsing. A partial unique index reserves each serial to at most one nonremoved registration, including disabled/unapproved registrations; requests cannot supply their own tenant. Removal closes every current link at the same database instant and retains the old registration, audit, users, events and employee history. It releases the serial for a fresh registration in the same or another business. The new row has a new device ID, unapproved/disabled state, reset sync stamp and no inherited users or links. Another business cannot remove, revive or edit the old registration.

Every new registration has an inclusive `accept_events_from` boundary at database registration time. Older punches are acknowledged and counted but skipped before inserting users or raw events; neither old employee PINs nor old evidence enter the new tenant. Mixed packets retain eligible punches, deduplicate retries and advance the stamp only after the entire transaction commits. Settings shows the count skipped in the last upload. Existing pre-migration registrations receive an unbounded historical start to preserve their established history and delayed uploads. Employee attribution still independently requires its effective link interval. Disable/enable preserves registration and links; remove/register starts a new lifetime.

Before handover, reconnect the terminal and verify pending old-business punches have arrived, then remove it, register/approve it in the new business, and explicitly link each new employee. The server cannot prove that an offline terminal has uploaded its entire backlog. Unsent older punches are not recovered through the new registration. Removal does not erase terminal fingerprints, users or logs: review/clear old enrollments on the physical machine before reuse and set its clock/timezone correctly. A wrong machine clock or fabricated serial cannot be made trustworthy by timestamp filtering. Connection freshness and last accepted upload are separate signals; recent contact does not establish complete synchronization.

**Known limitation, explicitly accepted for current development:** legacy attendance PUSH serial identification is not cryptographic authentication. Someone who knows an approved serial can impersonate it from another network and submit fabricated punches to its business. HTTPS protects transport and authenticates the server; approval alone does not prove the physical sender. Source IP is diagnostic metadata only and has no authorization role, allowing shared IPs, NAT, dynamic IPs and router changes. This is not a production-ready device-authentication system.

The [manufacturer's MB20-VL manual](https://s3.ap-southeast-1.amazonaws.com/zkteco.co.th/files/20240401/ZK_MB20-VL%C2%A0UM_EN%C2%A0v1.1_20220424_A4.pdf) documents ADMS domain mode, proxy and HTTPS; it does not establish a configurable upload key/challenge for the working legacy mode. PC Connection Comm Key must not be assumed to authenticate ADMS. Future hardening requires verified compatible firmware authentication or an agreed authenticated gateway. Do not silently require a key, relay or fixed IP for this development connection.

## Receiver reliability and operations

The receiver retains its scoped database role, bounded bodies/records/connections/concurrency, non-root read-only container and existing resource limits. Its private JWT can invoke only `attendance_receive`, with no table/financial access. Caddy blocks public REST ingestion, replaces source/TLS diagnostic headers and strips client authorization/cookies. Ordinary browser roles cannot invoke ingestion. No template, fingerprint image, face or name is requested or stored.

Supported routes remain `cdata`, `getrequest`, `ping`, `devicecmd` and `.aspx` variants. Attendance rows support the real MB20-VL's eleven bounded columns; only required attendance scalars are retained. Other bounded known upload types are discarded. The committed stamp and `OK: <count>` follow the database commit. Exact retries and overlapping distinct scans deduplicate; identical repeated rows in one packet retain separate evidence. Identical enrollment/second/field scans across packets cannot be distinguished from retries. Polling/retry behavior and machine settings remain unchanged.

Deploy through `deploy:all` with the exact pending migration versions. The established workflow validates source checksums, backs up database/roles, applies migrations transactionally, reloads PostgREST and updates dependent services before frontend publication. Logs contain route/status/counts and source diagnostics, never upload bodies, URLs or credentials.

Current checks: `npm run attendance:test`; `node supabase/tests/run-attendance.mjs --vps --with-migrations` before deployment (without that final flag afterward); `node supabase/tests/attendance-api.mjs --vps --browser`; build/lint and deployment tests. The DB runner clones the deployed PostgreSQL database into a newly named disposable database, tests only there and removes only that clone. `attendance.sql` and `employee-profile.sql` retain the historical migration replay contracts through `20261030035535`; the current contract is `attendance-phases.sql`; `attendance-history.sql` retains the former automatic-close contract. Live API/browser fixtures use isolated businesses and preserve original business fingerprints. Physical scans, terminal offline recovery and installed-device acceptance remain distinct from synthetic protocol/browser tests.
