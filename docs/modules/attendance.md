# Employee attendance

Attendance is independent of salary, bonuses, penalties and wallet accounting. Employee directory cards show Clocked in / Clocked out with the corresponding AM/PM time, or Not clocked in when no arrival is recorded; clocked-out cards retain the arrival time underneath. Loading and unavailable states remain explicit. Employee profiles show today's estimated attendance and a dedicated Attendance history dialog. Add employee and Edit employee contain device linking beside salary/status fields. Settings → Business profile contains attendance rules and device management.

## Workdays and summaries

- A workday starts at the configured cutoff in the business IANA timezone and ends at the following date's cutoff. Midnight (`00:00`) is the default. A 04:00 cutoff attributes 03:59 punches to the preceding date. Days use actual timezone instants, including 23/25-hour DST dates. Weekly summaries start Monday; monthly summaries use calendar months of workday labels. Inclusive date filters apply before aggregation.
- The earliest valid punch is clock-in and the latest strictly later punch is clock-out. Duplicate punches never add worked time. With only one distinct punch, clock-out remains open until the day's end, then reads as the saved boundary. Automatic closure is calculated on read, so it also works after downtime without a midnight job. Worked time is the closed interval, not the number of punches; open intervals show zero completed time.
- Raw device events retain terminal wall time, converted instant, received time, status/verification/workcode and clock warnings. Device dates more than ten minutes ahead of receipt remain quarantined even when wall time catches up. Supported device years are 2000–2100. Missing punches alone do not prove absence.
- Cutoff changes begin on the following local date. Effective rules determine both ends of a day, including the transition day. Saved past boundaries and delayed uploads use their historical rule. Timezone changes are rejected after any raw attendance or manual workday exists. Nonexistent DST wall times are rejected for manual corrections; ambiguous repeated wall times follow PostgreSQL's standard-time interpretation. Legacy terminal timestamps cannot disambiguate repeated DST times.
- Per-employee/day summaries combine eligible punches across machines. Ingestion updates only affected indexed ranges once per packet. Late and out-of-order uploads revise the correct day. Manual corrections take priority over later raw uploads. A corrected arrival with no departure follows the same automatic cutoff; clearing both times leaves the day not attended. Daily, weekly, monthly and activity reads all share the same authoritative projection.

## Effective linking and corrections

`attendance_links` stores immutable starts and one-way ends for each device/User ID/employee association. New links start at database server time; prior punches remain unassigned. A punch belongs to a link only within `[linked_at, unlinked_at)`, regardless of arrival time. Unlinking preserves old attendance and previous associations. Reusing a machine User ID starts another period and cannot transfer earlier evidence. Current links are unique by device/User ID and device/employee. Device locks serialize registration, removal, linking and ingestion. Employee creation and initial linking share the existing idempotent `save_employee` transaction; a failed link rolls back the employee too.

The one-time migration preserves previously adopted historical associations, which had no recorded effective start, with an explicit unbounded start. It does not backdate new links. The old departure-threshold configuration is retained in configuration audit before normalization to midnight. Raw machine events, stock and financial evidence are fingerprint-checked for preservation.

Owners and Managers with `employees:manage` can use Attendance history → Edit history. The date editor loads current times and a revision, then the standard confirmation dialog shows before/after values and the reason. SQL independently verifies trusted RBAC membership, tenant, date, ordered times within the saved day, future-time restrictions and revision. Empty clock-in/out marks a day as not attended. Append-only `attendance_adjustments` retain actor, reason, before values, final values and idempotency request ID; original events are never rewritten. Recent corrections are visible in the editor. A retry uses the original request ID. Concurrent or delayed device changes reject stale edits.

Activity contains stable `employee:date:in/out` identities, rather than every raw punch. A later clock-out updates that day's existing item. Capability gates keep payroll-only readers out of attendance and employee-only readers out of financial evidence. Histories filter and paginate on the server: attendance 12 periods/page, activity 12 items/page, raw-event audits and unlinked device users 25/page. Indexes cover tenant/employee/date, effective links, raw enrollment/date ranges, revisions and audit lookups.

## Direct ADMS and security limitation

The canonical `attendance-receiver/server.mjs` remains a machine-initiated ADMS PUSH service behind the existing Caddy HTTPS host on port 443. The connected MB20-VL's existing server address stays `api.lpg.144.79.249.4.sslip.io:443`; standalone port 4370 is unrelated and must not be publicly forwarded. No local relay, shop public IP, authentication key, firmware change or new infrastructure is required.

A Settings manager registers an exact serial into their trusted business, then explicitly approves it. Existing authorized machines remain approved during migration. Unregistered, unapproved, disabled and removed serials are rejected before upload parsing. A serial is globally reserved and resolves exactly one business; requests cannot supply their own tenant. Removal is a tombstone and ends current links while retaining all evidence. Connection freshness and last accepted upload are separate signals; recent contact does not establish complete synchronization.

**Known limitation, explicitly accepted for current development:** legacy attendance PUSH serial identification is not cryptographic authentication. Someone who knows an approved serial can impersonate it from another network and submit fabricated punches to its business. HTTPS protects transport and authenticates the server; approval alone does not prove the physical sender. Source IP is diagnostic metadata only and has no authorization role, allowing shared IPs, NAT, dynamic IPs and router changes. This is not a production-ready device-authentication system.

The [manufacturer's MB20-VL manual](https://s3.ap-southeast-1.amazonaws.com/zkteco.co.th/files/20240401/ZK_MB20-VL%C2%A0UM_EN%C2%A0v1.1_20220424_A4.pdf) documents ADMS domain mode, proxy and HTTPS; it does not establish a configurable upload key/challenge for the working legacy mode. PC Connection Comm Key must not be assumed to authenticate ADMS. Future hardening requires verified compatible firmware authentication or an agreed authenticated gateway. Do not silently require a key, relay or fixed IP for this development connection.

## Receiver reliability and operations

The receiver retains its scoped database role, bounded bodies/records/connections/concurrency, non-root read-only container and existing resource limits. Its private JWT can invoke only `attendance_receive`, with no table/financial access. Caddy blocks public REST ingestion, replaces source/TLS diagnostic headers and strips client authorization/cookies. Ordinary browser roles cannot invoke ingestion. No template, fingerprint image, face or name is requested or stored.

Supported routes remain `cdata`, `getrequest`, `ping`, `devicecmd` and `.aspx` variants. Attendance rows support the real MB20-VL's eleven bounded columns; only required attendance scalars are retained. Other bounded known upload types are discarded. The committed stamp and `OK: <count>` follow the database commit. Exact retries and overlapping distinct scans deduplicate; identical repeated rows in one packet retain separate evidence. Identical enrollment/second/field scans across packets cannot be distinguished from retries. Polling/retry behavior and machine settings remain unchanged.

Deploy through `deploy:all` with the exact pending migration versions. The established workflow validates source checksums, backs up database/roles, applies migrations transactionally, reloads PostgREST and updates dependent services before frontend publication. Logs contain route/status/counts and source diagnostics, never upload bodies, URLs or credentials.

Current checks: `npm run attendance:test`; `node supabase/tests/run-attendance.mjs --vps --with-migrations` before deployment (without that final flag afterward); `node supabase/tests/attendance-api.mjs --vps --browser`; build/lint and deployment tests. The DB runner clones the deployed PostgreSQL database into a newly named disposable database, tests only there and removes only that clone. `attendance.sql` and `employee-profile.sql` retain the historical migration replay contracts through `20261030035535`; the current contract is `attendance-history.sql`. Live API/browser fixtures use isolated businesses and preserve original business fingerprints. Physical scans, terminal offline recovery and installed-device acceptance remain distinct from synthetic protocol/browser tests.
